# Amazon GuardDuty

> Crate: [`mws-guardduty`](../../crates/services/mws-guardduty) · Tests: [`tests/e2e-rust/tests/e2e/guardduty.rs`](../../tests/e2e-rust/tests/e2e/guardduty.rs), [`guardduty_detection.rs`](../../tests/e2e-rust/tests/e2e/guardduty_detection.rs)

All 102 operations are generated from the AWS model (restJson1) and implemented. Enabled detectors analyse the CloudTrail management events MWS records and raise real findings for a set of deterministic detections (below). VPC flow logs, DNS logs, EKS audit logs, S3 data events and runtime events are not analysed, and there is no anomaly detection (`*/AnomalousBehavior`) or AWS-curated threat intelligence (`MaliciousIPCaller`, `TorIPCaller`); those types exist only as samples.

✅ supported · 🟡 partial · ❌ not supported

| Feature | Status | Details |
| --- | :---: | --- |
| Detectors | ✅ | One per account and Region, publishing frequency, enable/disable, tags with `aws:ResourceTag` and `aws:RequestTag` conditions. The first `CreateDetector` creates `AWSServiceRoleForAmazonGuardDuty` in IAM (it shows in `ListRoles`), which needs `iam:CreateServiceLinkedRole` (`iam:AWSServiceName` `guardduty.amazonaws.com`) unless the role exists; `EnableOrganizationAdminAccount` creates it in the delegated administrator. Member detectors that an administrator enables for organization accounts do not create the role. |
| Threat detection | 🟡 | From CloudTrail management events, in accounts and Regions with an enabled detector: `Policy:IAMUser/RootCredentialUsage` (any root call), `Stealth:IAMUser/CloudTrailLoggingDisabled` (`StopLogging`, `DeleteTrail`), `Stealth:IAMUser/PasswordPolicyChange` (`DeleteAccountPasswordPolicy`, or an `UpdateAccountPasswordPolicy` weaker than the policy GuardDuty last saw set), `Policy:S3/BucketBlockPublicAccessDisabled`, `Policy:S3/AccountBlockPublicAccessDisabled` (a Block Public Access setting turned off or deleted), `Policy:S3/BucketAnonymousAccessGranted` (a bucket policy allowing `*` without conditions, or an ACL granting `AllUsers`), `Stealth:S3/ServerAccessLoggingDisabled`, and `UnauthorizedAccess:IAMUser/MaliciousIPCaller.Custom` / `Recon:IAMUser/MaliciousIPCaller.Custom` (a write / read-only call from an address on an active threat list). Findings carry AWS's resource (`AccessKey` or `S3Bucket` with `accessKeyDetails`), `AWS_API_CALL` action (API, service, caller IP, user agent, affected resources) and threat list evidence. Repeats aggregate into one finding per type, principal and resource (`service.count`, `eventLastSeen`). Calls from addresses on active trusted lists raise nothing. Configuration findings need the call to have succeeded. GuardDuty's own API calls are not analysed (so sample-finding workflows stay clean). Source addresses are what CloudTrail records as `sourceIPAddress` (the client's socket address; `X-Forwarded-For` is not trusted). |
| Protection plans | ✅ | `Features` (S3, EKS audit logs, runtime monitoring with additional configuration, EBS malware, RDS, Lambda, AI protection) and the legacy `DataSources`, kept consistent; mixing both in one request is rejected as AWS does. |
| Sample findings | ✅ | Every finding type (about 190) with AWS's sample shape: `[SAMPLE]` titles, `GeneratedFinding*` placeholders, `additionalInfo.sample: true`, per-type severity and resource. Generating a sample again increments `service.count`. |
| Finding queries | ✅ | `ListFindings` and `GetFindingsStatistics` with finding criteria (`Eq`, `Neq`, `Equals`, `NotEquals`, `Gt`/`Gte`/`Lt`/`Lte`, `Matches` wildcards) over any finding attribute, sorting, pagination, every `GroupBy`. |
| Archive and feedback | ✅ | Archive, unarchive and feedback; a member managed by an administrator cannot archive its own findings. |
| Filters | ✅ | `NOOP` and `ARCHIVE` (suppression rules) with ranks; suppressed findings are archived and not published. An administrator's suppression rules apply to its members. |
| EventBridge | ✅ | `GuardDuty Finding` events (source `aws.guardduty`) for new and updated findings, in the finding's account and its administrator's; malware object scans send `GuardDuty Malware Protection Object Scan Result`. Detected findings are published (to EventBridge, Security Hub and publishing destinations) five minutes after they are first seen, and updates of a recurring finding on the detector's `FindingPublishingFrequency` (`FIFTEEN_MINUTES`, `ONE_HOUR`, `SIX_HOURS` by default), on the emulated clock (`/_mws/clock`); they show in `ListFindings` at once. Sample and malware findings (and their updates) are published at once. |
| Publishing destinations | ✅ | Findings written to S3 as gzipped JSON Lines under `AWSLogs/<account>/GuardDuty/<region>/`, as `guardduty.amazonaws.com` with SSE-KMS under the destination's key (bucket and key policies apply). Failures show as `UNABLE_TO_PUBLISH_FIX_DESTINATION_PROPERTY`. |
| Security Hub | ✅ | New and updated findings are imported as ASFF from product `aws/guardduty` (types, severity labels, resources, `aws/guardduty/...` product fields) when the account has Security Hub enabled. |
| Threat lists | ✅ | IP sets, threat intel sets, threat entity sets and trusted entity sets with AWS's limits. Activating a list (create, `Activate`, or a new location) makes it `ACTIVATING`; five seconds later on the emulated clock GuardDuty reads the file from S3 (`s3://`, path-style or virtual-hosted HTTPS URLs) and the list is `ACTIVE`, or `ERROR` when the bucket or object is missing, `ExpectedBucketOwner` does not match, a bucket in another account does not allow `guardduty.amazonaws.com`, or the file holds no valid entries. `TXT` takes one IP address or CIDR range per line (and domains in entity sets; `#` comments); `STIX`, `OTX_CSV`, `ALIEN_VAULT`, `FIRE_EYE` and `PROOF_POINT` take every IP address and CIDR range in the file. Active threat lists drive the `MaliciousIPCaller.Custom` findings and active trusted lists suppress findings. Creating or updating a list needs `iam:PutRolePolicy`, and deleting one `iam:DeleteRolePolicy`, on the GuardDuty service-linked role. Deactivating is immediate (`INACTIVE`); `DEACTIVATING` and `DELETE_PENDING` are not reported. Domain entries are kept but not matched (no DNS analysis). |
| Members by invitation | ✅ | Create, invite, accept (also the deprecated master operations), decline, delete, disassociate, stop and start monitoring, member detector features; the administrator sees members' findings. |
| Organizations | ✅ | `EnableOrganizationAdminAccount` (management account) enables trusted access and registers the delegated administrator in Organizations; the administrator adds organization accounts as members without invitations, `AutoEnableOrganizationMembers` `ALL`/`NEW` enables detectors and features as accounts appear, organization statistics. |
| Malware Protection for S3 | ✅ | Plans work in S3 as their role (`malware-protection-plan.guardduty.amazonaws.com` must be trusted): creating one turns on EventBridge notifications for the bucket, or leaves the plan in `ERROR` with the reason. New objects under the plan's prefixes are scanned as they are created (and by `SendObjectMalwareScan`), tagged `GuardDutyMalwareScanStatus` when tagging is enabled, and reported as `GuardDuty Malware Protection Object Scan Result` events; infected objects also raise `Object:S3/MaliciousFile` findings. The scanner detects the EICAR test file, which is how AWS documents testing it; MWS has no signature database for real malware. |
| EBS malware scans | 🟡 | `StartMalwareScan` and scan history are kept, and every scan completes immediately as `NO_THREATS_FOUND`. |
| Custom detection rules | 🟡 | A small built-in catalog with associations (`DRY_RUN` expires, `LIVE`) and organization configurations; rules do not run. |
| Investigations | 🟡 | Stored and complete immediately with no results. |
| Coverage and usage | 🟡 | Coverage is empty, usage costs are zero, free trial days are 30. |
